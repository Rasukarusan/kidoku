# コレクション管理への移行設計

状態: 実装対象の設計。移行SQLの適用・本番切り替えは運用手順に従って実施する。

## 目的と方針

本、映画、ゲーム、展示などを扱えるコレクション管理アプリにする。
ドメイン、テーブル、API、URL、画面の用語をコレクションとアイテムに統一する。
既存の `Book` / `Sheet` を新設計の制約にはしない。

初期提供する種類は本と映画。種類の追加を、共通テーブルやCRUDの追加変更なしで行える構造にする。
ユーザーが独自の種類を作る編集画面や、全ユーザー共通の作品カタログは初期範囲に含めない。

既存の拡張性調査: [GENERAL_PURPOSE_RECORDS_ASSESSMENT.md](./GENERAL_PURPOSE_RECORDS_ASSESSMENT.md)

## 中心となる概念

| 概念       | 責務                             | 例                                       |
| ---------- | -------------------------------- | ---------------------------------------- |
| Collection | ユーザーが自由に作るまとめ先     | お気に入り、2026年、旅行先で出会った作品 |
| Item       | ユーザーが管理する対象           | ある本、映画、ゲーム                     |
| ItemType   | 種類に固有の構造と振る舞いの定義 | 本の著者・ISBN、映画の監督・上映時間     |
| ItemLog    | 対象についての出来事・体験の記録 | 読了、鑑賞、クリア、購入                 |

コレクションとアイテムは多対多。同じアイテムを「映画」と「お気に入り」に入れても、アイテムや鑑賞数は増えない。
コレクションには複数種類のアイテムを混在させられる。
アイテムはユーザーごとに所有し、別ユーザーの同じ作品とは独立して編集する。
コレクション未所属のアイテムも保持できる。

年・月は履歴の日付から集計する。コレクション名の `2026` を年の条件とは解釈しない。
種類、期間、コレクションは独立した絞り込み条件として扱う。

## テーブル構成

| テーブル           | 主な列                                                                                                                                                                                           | 責務                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| `collections`      | `id`, `user_id`, `name`, `description`, `position`, `created_at`, `updated_at`                                                                                                                   | まとめ先                                                  |
| `item_types`       | `id`, `key`, `name`, `schema_version`, `definition`                                                                                                                                              | 種類の定義。`key` は `book`, `movie` などの安定した識別子 |
| `items`            | `id`, `user_id`, `item_type_id`, `title`, `image_url`, `category`, `rating`, `memo`, `is_public_memo`, `is_purchasable`, `price`, `attributes`, `attributes_version`, `created_at`, `updated_at` | 共通属性と種類固有の属性                                  |
| `collection_items` | `collection_id`, `item_id`, `position`, `added_at`                                                                                                                                               | 所属関係。`collection_id + item_id` は一意                |
| `item_logs`        | `id`, `item_id`, `kind`, `occurred_at`, `memo`, `rating`, `created_at`, `updated_at`                                                                                                             | 複数回の読了・鑑賞などの履歴                              |

名前、主キーの型、文字数などの細部は実装時に既存DBとの整合を取る。
`items.rating` は対象への総合評価、`item_logs.rating` はその回の評価。両者は独立させ、暗黙に上書きしない。
既存の評価記号は移行時に維持する。
履歴がなくてもアイテムを登録できるため、未読・未鑑賞の対象や所有品も管理できる。
`occurred_at` 未設定の履歴は日付不明として保持し、年・月別の集計対象から外す。

所属追加時はコレクションとアイテムの所有者の一致を検証する。
既存スキーマは `relationMode = "prisma"` のため、物理FKの有無に依存せず、所属操作・削除はトランザクションとリポジトリで整合性を保証する。
`collection_items.item_id`、`items(user_id, item_type_id)`、`item_logs(item_id, occurred_at)` に必要な索引を設ける。
コレクション削除は所属関係のみを削除し、アイテムを残す。アイテム削除時は所属と履歴をまとめて削除する。

## 種類の定義

`item_types.definition` は、以下を持つバージョン管理されたJSON定義とする。

- 固有フィールドのキー、表示名、型、必須条件、入力上限、選択肢。
- 一覧や詳細での表示順序。
- 利用可能な履歴の種類と日時ラベル。本なら `read` / 読了日、映画なら `watched` / 鑑賞日。
- アイテム数と履歴数の単位。本なら「冊」「回」、映画なら「作品」「回」。
- 外部検索・取り込みのプロバイダーキーと、利用可能な分析機能のキー。

本の `attributes` 例: `{ "authors": ["著者名"], "isbn": "..." }`。
映画の例: `{ "directors": ["監督名"], "releaseYear": 2026, "runtimeMinutes": 120 }`。
監督を `author` に保存するような読み替えは行わない。

種類定義と属性はAPI側で検証し、フォームは同じ定義を参照する。
外部検索、特殊なUI、AI処理はコード内の許可済みハンドラーをキーで選ぶ。DBには実行コードを保存しない。
新しい種類は定義の追加で手入力・共通CRUD・一覧表示に対応し、専用検索や分析が必要ならハンドラーを追加する。

よく検索する共通属性は通常列に置く。種類固有の属性を検索・集計する必要が増えた場合は、対象を選んで索引や専用テーブルへ切り出す。
定義の変更は既存アイテムを突然無効にせず、属性バージョンに応じた変換・バックフィルを用意する。
履歴のあるアイテムの種類変更には、属性と履歴の変換が必要。初期段階では直接の種類変更を許可しない。

## 操作と表示

1. アイテム登録時に種類を選ぶ。
2. 種類に対応する検索か手入力で、共通属性と固有属性を入力する。
3. 任意のコレクションへ追加する。登録と所属追加は一括して確定する。
4. 読了・鑑賞などを記録するときに履歴を追加する。再読・再鑑賞は同じアイテムへの新しい履歴になる。

コレクション一覧・アイテム一覧は共通UIを使い、種類固有の入力・表示部分を差し替える。
映画は初期段階では手入力。本のISBN検索・バーコード読み取りは本の機能として維持する。
外部検索結果から登録する場合も、共通の登録経路に正規化して取り込む。

集計では「登録アイテム数」と「体験・出来事の回数」を明確に区別する。
複数コレクションを横断したアイテム数はIDで重複排除する。
混在した一覧の総数は「件」で表示し、種類別では定義された単位を使う。
既存の読書分析は `book` と `read` の履歴を対象とする。分析ごとに対象種類・履歴・期間・結果スキーマを明示する。
CSV、OGP、検索、MCPにも種類と固有属性を反映する。

メモの公開設定はアイテム単位で維持する。コレクションへの所属で非公開メモの権限が変わることはない。
履歴のメモは初期段階では所有者にのみ返し、公開機能を追加する際に明示的な公開設定を設ける。
履歴の保存と外部サービス・検索インデックスへの出力は分け、公開可能な情報だけを投影する。

## 既存データ・契約の移行

| 現在                           | 移行先                                                                                            |
| ------------------------------ | ------------------------------------------------------------------------------------------------- |
| `sheets`                       | `collections`。IDと名前を維持                                                                     |
| `books`                        | `items`。IDと所有者を維持し、種類は `book`                                                        |
| `books.sheet_id`               | `collection_items` の所属行                                                                       |
| `books.author`                 | 本の `attributes.authors`。元の文字列を分割せず保持                                               |
| `books.impression`             | `items.rating`                                                                                    |
| `books.finished`               | 日付がある場合に `item_logs(kind = read)` を1件作成。総合メモ・評価はアイテム側に維持             |
| `book_comments` / `book_id`    | `item_comments` / `item_id`                                                                       |
| いいね・購入・通知の `book_id` | `item_id`                                                                                         |
| `template_books`               | `item_templates`。種類と属性を持つ登録テンプレート                                                |
| `yearly_top_books`             | `collection_highlights`。コレクション内のお気に入り順位。暦年のベスト表示は実日付の条件を別途使う |
| `ai_summaries.sheet_id`        | コレクションへの参照。分析対象条件・分析種類・結果バージョンを明示                                |

既存の年間ベストは、ユーザーと旧 `year` 文字列に一致する旧シートを照合して所属コレクションへ移す。
照合できない行は削除・推測せず、移行前に検出して解決する。
過去のAI分析は読書分析の既存結果として保持し、汎用分析の結果として読み替えない。
日付がないアイテムに読了履歴を捏造しない。旧シート名と実日付の不整合は報告し、日付を自動補正しない。

新しいドメイン・APIは `Collection` / `Item` / `ItemLog` に統一する。
正規URLは `/items/:id` と `/:user/collections/:id` にし、表示名の変更でリンクを壊さない。
旧URLはIDや旧名を解決してリダイレクトする。既存REST・GraphQL・MCPの利用経路には移行期間中の互換アダプターを置き、新規コードは新しい契約だけを使う。
互換APIで見える対象は本に限定し、映画などをBookとして返さない。

移行は、参照先を保つテーブル・列のリネーム、属性と所属・履歴のバックフィル、参照コードの切り替えを明示したSQLと手順で行う。
本番のテーブル名変更を `prisma db push` の自動判定に任せない。
Web/APIの両Prismaスキーマ、検索インデックス、公開ページ、エクスポート、テストを一緒に更新する。
DB変更を含む移行では書き込みを止めてバックアップを取得し、旧・新バージョンが同時に書き込まない切り替え手順を用意する。
件数・ID・所有者・所属・メモ・購入参照の照合後に切り替える。失敗時は旧コードと切り替え前のDBへ戻せる手順を事前に検証する。

## 検証する主要な動作

- 既存の本・メモ・公開設定・購入・コメント・リンクが移行後も対応する。
- 映画の登録・編集・鑑賞履歴・削除が共通のAPIとUIで完結する。
- 同じアイテムの複数所属で件数が水増しされず、コレクション削除でアイテムが失われない。
- 再鑑賞はアイテム1件・鑑賞2回となり、日付不明は期間集計に入らない。
- 別ユーザーのアイテムへの所属追加・更新・非公開情報の取得を拒否する。
- 第三の種類を定義だけで追加し、共通CRUD・フォーム・一覧が動く。
- 読書集計・分析に映画や他種別が入らない。

## 実装上の互換層

旧 `Book` / `Sheet` の読み取りは `legacy_books` / `legacy_sheets` / `legacy_template_books` / `legacy_collection_highlights` のSQLビューを通す。
物理データの保存先は新しい汎用テーブルのみとし、旧APIからの書き込みも新テーブルへ変換する。
互換Bookのシートは所属IDの最小値、読了日は最後に追加した読了履歴を投影する。
複数所属・履歴全体・未所属アイテムは新しいItem APIで取得する。
本の購入・コメント表示と読書分析の画面は互換コンポーネントを再利用する。
本以外の種類は汎用画面を使い、Book APIには流さない。

移行手順と検証範囲は [COLLECTION_MIGRATION.md](./COLLECTION_MIGRATION.md) を参照。
